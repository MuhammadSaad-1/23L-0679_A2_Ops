1. SECRETS MANAGEMENT IN GITHUB ACTIONS:
----------------------------------------------------------------------
A. WHERE WORKFLOW SECRETS ARE STORED:
   - In GitHub: Navigate to your repository -> Settings -> Secrets and variables -> Actions.
   - Click "New repository secret" to add keys such as `DAGSHUB_TOKEN`, `DB_PASSWORD`, etc.
   - Internally, GitHub encrypts these values at rest using Libsodium sealed boxes
     (public-key cryptography). The plaintext is accessible ONLY to GitHub Actions
     runners at the precise moment a job executes.

B. WHY SECRETS MUST NEVER APPEAR IN THE WORKFLOW FILE (.github/workflows/ci.yml):
   - Public Exposure & Git Immortality:
     Workflow files (`ci.yml`) are committed directly to Git. If secrets are hardcoded,
     anyone viewing your public repository (or forking it) has immediate, permanent
     access to your cloud tokens, databases, and private registries. Even if you delete
     the commit later, Git history preserves the plaintext unless the entire repository
     is forcefully purged with `git-filter-repo`.
   - Log Masking:
     When referenced via `${{ secrets.MY_SECRET }}`, GitHub Actions automatically masks
     any matching output string in execution console logs with `***`. Hardcoded strings
     are NOT masked and will leak into build log archives.

3. PRODUCTION VISIONGUARD CI PIPELINE ARCHITECTURE:
----------------------------------------------------------------------
The file `.github/workflows/ci.yml` implements a 2-stage automated pipeline:
- Stage 1 (`lint-and-test`):
  Runs across a matrix of Python 3.10 and Python 3.11.
  Executes Flake8 syntax and complexity checks, followed by Pytest on the application
  routes, in-memory inference pipeline, and error handlers.
- Stage 2 (`docker-build`):
  Executes only after Stage 1 passes. Builds the production Docker image, boots a
  container, and runs an automated `curl` probe against `/health` to verify container readiness.
